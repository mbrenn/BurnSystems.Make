= BurnSystems Make

== Use

To use _BurnSystems.Make_, call 'bsmake [verb] [options]'.

 bsmake [verb] [-c|--configuration <configuration>]

The following verbs are supported: 

* clean: Cleans the current folder
* build: Builds the folder

The following options are supported:

* -c, --configuration <configuration>: Specifies the build configuration (e.g., `Debug`, `Release`). If specified, it is forwarded to the build agent executable and to the underlying `dotnet build` / `dotnet clean` commands.

BurnSystems.Make supports the execution within a solution-context and a project-context.
The solution-context is automatically figured out by having a .sln or .slnx-file within the current directory. 

=== Solution-Context

Within solution-context, it is assumed that _BurnSystems.Make_ calls MSBuild. Due to technical limitation of the Solution Files (.sln[x]), an external tool cannot be called from the Solution File.

That means, it is assumed that _BurnSystems.Make_ gets called by the user or build pipeline. It will then perform the following steps: 

. Check, if a Build Agent is specified for the Solution and executes it with the given configuration (<<build-and-call-of-the-build-agent>>).
. Execute 'dotnet build' (forwarding '-c <configuration>' if specified) to start building of the included projects.

When calling 'clean', it performs the following steps:

. Clean the Build Agent if specified for the Solution.
. Execute 'dotnet clean' (forwarding '-c <configuration>' if specified).

=== Project-Context

==== Adding a Build Agent

The Build Agent can be added by creating a .bsmake directory and implementing the Build Agent within that directory.

A description how potential Build Agent can look like is defined in <<build-agent-definition>>

==== Enabling the Build Agent

Within project-context, it is expected that _BurnSystems.Make_ is called before target 'CoreCompile' (for `build`) and before target 'Clean' (for `clean`) by MSBuild.

This can be easily achieved by adding the following targets to the Project-Configuration:

 <Target Name="RunBSMake" BeforeTargets="CoreCompile">
   <Exec Command="bsmake build $(MSBuildProjectDirectory) -c $(Configuration)" />
 </Target>
 <Target Name="RunBSMakeClean" BeforeTargets="Clean">
   <Exec Command="bsmake clean $(MSBuildProjectDirectory) -c $(Configuration)" />
 </Target>

Potential entry points are the specific .csproj-files or if you would like to get _BurnSystems.Make_ in project-context called per each project, you can add it to the 'Directory.Build.Targets' on Solution-Level:

 <Project>
   <Target Name="RunBSMake" BeforeTargets="CoreCompile">
     <Exec Command="bsmake build $(MSBuildProjectDirectory) -c $(Configuration)" />
   </Target>
   <Target Name="RunBSMakeClean" BeforeTargets="Clean">
     <Exec Command="bsmake clean $(MSBuildProjectDirectory) -c $(Configuration)" />
   </Target>
 </Project>

If _BurnSystems.Make_ gets called in project-context, it is assumed that it gets called by a build tool. It performs the following step:

. Check, if a Build Agent is specified for the project and executes it with the corresponding verb (`build` or `clean`) and configuration. (<<build-and-call-of-the-build-agent>>)

=== Summary

Let's assume the following solution (Directories in _italic_)

* _Example_
** Example.slnx
** _Example_Library_
*** Example_Library.csproj
** _Example_Executable_
*** Example_Executable.csproj

This can be enriched to a full _BurnSystems.Make_ project by adding the following files. There is no need to add a .bsmake project for every project. In that example, we skip it for Example_Executable. 

* _Example_
** Example.slnx
** Directory.Build.targets
** _.bsmake_
*** Build.csproj
** _Example_Library_
*** _.bsmake_
**** Build.csproj
*** Example_Library.csproj
**** Build.csproj
*** Example_Executable.csproj

The calls between_BurnSystems.Make_ will be performed as the following: 

* 'Example': User/Pipeline calls bsmake (not MSBuild!)
** 'Example': bsmake identifies Build Agents, builds it and executes it
** 'Example': bsmake calls msbuild for Example.slnx
** 'Example': MSBuild identifies projects and builds them
*** 'Example Library': MSBuild starts bsmake via Directory.Build.targets before compiling
**** 'Example Library': bsmake identifies Build Agents, builds it and executes it
*** 'Example Library': MSBuild continues to build the full c# project
*** 'Example Executable': MSBuild starts bsmake via Directory.Build.targets before compiling
**** 'Example Executable': bsmake identifies that no build agent is existing and skips itself
*** 'Example Executable': MSBuild continues to build the full c# project

This example is also available under https://github.com/mbrenn/BurnSystems.Make/tree/main/src/Example

[[build-agent-definition]]
=== Build Agent Definition
A implementation of Build Agent usually resides in the .bsmake directory relative to the corresponding solution or project.

At the moment, there is only one type of Build Agent supported: 

. Executable

Hint: You can exclude the *.cs files from the hosting project by removing the files via 'None' in the Project.csproj:

 <ItemGroup>
    <None Include=".bsmake\Build.cs" />
 </ItemGroup>

==== Build Agent as Executable

The Build Agent as Executable is created as a normal .Net Console Project. It minimally consists of a .csproj-file and the Source file. 
One example is available at link:https://github.com/mbrenn/BurnSystems.Make/tree/main/src/Example/Example.Library/.bsmake[Example Build Library].

The 'OutputType' of the Project must be Exe. 

The project is built via standard MSBuild procedure and called via 'StartProcess'. The return code is evaluate upon failure.

The Build Agent can optionally reference the `BurnSystems.Make.BuildAgent` helper library (package/assembly) which offers utilities such as:

* `BsMake`: Helper class to easily handle commands and dispatch tasks based on the active verb (`make.Verb(Verbs.Build, ...)` / `make.Verb(Verbs.Clean, ...)`).
* `Verbs`: Standard constants for supported verbs (`Verbs.Build = "build"`, `Verbs.Clean = "clean"`).
* `ProgramArguments.Parse(args)`: Parses the command-line arguments passed to the build agent executable to access properties like `Verb` (`arguments.Verb`) and `Configuration` (`arguments.Configuration`).
* `NpmHelper`: Utilities for npm/npx execution, installation verification (`InstallIfNotInstalled`), and module directory cleanup (`DeleteNodeModules`).
* `FileHelper.MergeFiles(options)`: Merges files with modification date checks (`OnlyIfModified`) and custom prefix headers, returning a boolean indicating if files were modified.
* `DirectoryHelper.CopyFiles(...)` / `DirectoryHelper.CopyFilesRecursively(...)`: Copies files matching search patterns non-recursively or recursively with subdirectories.
* `ProcessInvoke.Run(...)`: Runs external processes or commands with cross-platform PATH and extension resolution.
* `EnvironmentHelper`: Utilities for operating system and architecture detection.

For full API documentation and examples, see link:buildagent.adoc[Build Agent Documentation].

[[build-and-call-of-the-build-agent]]
=== Build and call of the Build Agent

In case _BurnSystems.Make_ is called, it looks for a .bsmake sub-directory and determines the Buildagent type. 

* In case, it is not existing: Nothing is performed -> No specific Buildagent required
* In case a .csproj file exists, a build agent is assumed. Currently, only 'Executable'-Buildagents are supported which are built and started

The building of the Buildagent via MS Build will only be triggered in case the .cs-files within that folder have a more recent state than the executable. If the executable is up-to-date, no build is executed. When building the Build Agent itself, the configuration is intentionally ignored so that the agent is not unnecessarily recompiled when only switching build configurations.

After the executable is available, it is being called by _BurnSystems.Make_. The active verb (`build` or `clean`) is passed as an argument. If a configuration was provided to _BurnSystems.Make_, `-c <configuration>` is also passed as argument to the executable. The working directory is the same as where the solution-file or project-file exists. In case the Buildagent wants to write a file, it can just call File.WriteAllText().

The Build Agents do not necessarily be part of the owning solution as _BurnSystems.Make_ will identify the existing via the files. 

== Realization Design

The repository consists of two solutions: 

* Tool: Contains the actual executable, its library and testing. This describes the actual BurnSystems Make deliverable
* Example: Just an example of how to integrate it. It is also used for testing purposes.

=== Tool Solution

* Project 'BSMake' contains the parsing for the command line and immediately calls the library
* Project 'BSMake.Library' (or 'BurnSystems.Make') contains all required orchestration logic
* Project 'BurnSystems.Make.BuildAgent' contains helper utilities for build agents (e.g. `ProgramArguments`, `FileHelper`)
* Project 'BSMake.Test' (or 'BurnSystems.Make.Test') contains the testing infrastructure. It also used the Example library.
